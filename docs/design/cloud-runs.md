# Cloud runs

This page explains how the daemon could hand one workflow step to a Claude cloud session, which
works on Anthropic's machines and reports by opening a pull request. It builds nothing. It holds
the model, the first code slice with its tests, the slices after it, and the open questions with a
recommendation for each.

A cloud session is not a run as Priory knows one. Priory's hooks and tool guard cannot run inside
it, and it cannot reach the `ask` tool. So the page is mostly about what may run there, and how
Priory keeps its gates around work it cannot watch.

Three facts about the CLI come from the coordinator of this design round, and this note did not
test them:

- `claude --cloud PROMPT` creates a session and prints its id.
- `claude -p MSG --cloud ID` sends that session a message.
- A session reports only by its pull request.

## What existed when this note was written

- An agent's `harness` is `claude-code` or `codex` (`crates/priory-factory/src/factory.rs:845`).
- A harness is a program Priory starts in tmux: the trait gives its name, its arguments, its trust
  step and a file (`crates/priory-runtime/src/runtime.rs:545`), and `launch` starts it in a
  detached session in the task's worktree (`runtime.rs:782`). [codex.md](../daemon/codex.md) lists
  each duty a harness has, side by side.
- Every duty relies on the run being local: the hook signals, the outbox that types only when the
  agent is idle, the tool guard's `PreToolUse` hook, the `priory` MCP server on the daemon's
  socket, and token counts read from the session's transcript file
  ([trace.md](../daemon/trace.md)).
- A run is admitted only when the runner has room for the agent's `memory` and `disk`
  ([room.md](../daemon/room.md)).
- A task owns its branch and its pull request, and events that name them route to it. Feedback on
  the pull request fires a wait with one line that names who said what
  ([waits.md](../daemon/waits.md#feedback-on-a-pull-request)).
- A task with a pull request that reaches `done` first waits on that pull request's checks at the
  result's commit. It is done when they are green, when the pull request merged, or when the
  commit has no check run at all. A task with no result at all is done with no gate
  ([waits.md](../daemon/waits.md#done-and-checks)).
- In the PRD's example workflow, `open-pr` is `irreversible`, and a human step approves it
  ([prd.md](../prd.md#workflows)).
- The state file's migrations are one numbered list, at `PRAGMA user_version = 88` when this note
  was written (`crates/priory-core/src/state.rs:1588`, `:1592`). Two branches that each add
  number 89 cannot both merge as they are.
- Cloud sessions already write pull requests to this repository by hand. Their branches are named
  `claude/<slug>-<suffix>`, such as #288 and #289, which both changed the migrations list. #257
  ended its body with a line the factory's writing rules do not have:
  `_Generated by [Claude Code](https://claude.ai/code)_`.

## The model

### What a cloud run is

An agent with `harness = "claude-cloud"` runs its steps in a cloud session. A cloud run has a row
in `runs` like any run, with the cloud session's id, and none of the rest: no tmux session, no
worktree, no hooks and no MCP server.

| Priory duty | Local run | Cloud run |
| ----------- | --------- | --------- |
| Start | `claude` in tmux, in a worktree | `claude --cloud PROMPT`, from the task's clone |
| Room | the agent's `memory` and `disk` | none: see [The laptop](#the-laptop) |
| Prompt delivery | pasted when idle, confirmed by a hook | sent at once, confirmed by the command's exit |
| Result | the `result` tool | the pull request the daemon finds |
| Question to a person | the `ask` tool | none |
| Sleep on an event | the `wait` tool | the daemon registers the waits itself |
| Tool guard | `PreToolUse` hook | none |
| Permission policy | the agent's `permissions` | the cloud environment's own |
| Proof | `priory gate` | none: the pull request's checks |
| Skills, memories, writing guide | plugin folder and system prompt | text in the prompt |
| Tokens | the transcript file | unknown |
| Health | exit, timeout, permission prompt | a deadline |

### What may run there

The work must be reversible and must end in a pull request. Nothing else comes back, so no other
kind of step can report.

The step itself is declared `effect = "irreversible"`. Its work can be undone, and its report
cannot: the session opens a pull request, which is what `open-pr` does, and the starters mark
`open-pr` irreversible. So the approval rule applies unchanged, with no new exception for
`priory check` or `priory check --explain` to learn: a human step lists the cloud step in
`approves` on every path that reaches it, or the step carries `autonomous = "<reason>"`.

An approval covers a commit. A task that ran a local step first, such as a plan, has its branch.
For a task that starts at a cloud step, the daemon creates the task's branch at its base commit
with no worktree, so the approval binds as it does today. The usual shape is a local plan step, a
person's approval of the plan, then the cloud step.

`priory check` refuses, with file and line:

- a `claude-cloud` agent at a step whose effect is not `irreversible`;
- a cloud step whose `next` has an outcome other than `opened`, `silent` and `failed`;
- a cloud step with a `proof`, a `guard`, a `plan_requires` or an `after`;
- a `claude-cloud` agent with `session = "shared"`, `mcpServers`, `permissions`, `memory` or
  `disk`, or named as a trigger's `lead`;
- a workflow where a path from a cloud step reaches `done` without passing a human step, since
  nobody would have read the session's work.

### The merge stays behind Priory's gate

The session holds its own GitHub credentials, and no guard reads its commands. Priory cannot stop
it from running `gh pr merge`. So GitHub must refuse the merge, and Priory must check that it
will before it sends any work.

Before each dispatch, the daemon reads the default branch's rules from GitHub and refuses to
dispatch unless they require a status check named `priory/gate` and apply to administrators too.
The task blocks with `cloud step implement: owner/name's default branch does not require
priory/gate, so a cloud session could merge its own pull request`.

The daemon sets that status, on one commit, when the workflow's merge step is approved at that
commit. A status belongs to a commit, so a new head has none and the approval is asked again, as
[tools.md](../daemon/tools.md#approvals) describes for any approval. An approval can also end
while the commit stays: a revive or a reopen starts a new generation. The daemon then sets
`priory/gate` to `failure` on that commit, with `approval withdrawn`. At each start, and on each
event of a cloud task's pull request, it compares the status on the head with the approval it
holds, and corrects the status when they differ. The merge is then Priory's
merge step, irreversible and approved by a person, as for any pull request.

One fact decides whether this holds, and this note could not check it: whether the session's own
credentials can set that status. If they can, the rule must also name who may set it, which
GitHub's rulesets allow for a GitHub App, and the check before a dispatch must then verify that
writer too. Open question 2 says to answer it by hand before the
first slice, and not to ship cloud runs on a guess.

A pull request of a cloud task that merges with no approved merge step gets a desk item, `merged
outside the gate`. That is detection for the case where the rules changed after the dispatch.

### The life of a cloud run

1. **Dispatch.** The daemon records the attempt, then runs `claude --cloud PROMPT` and stores the
   id it prints. A daemon that crashed between the two marks the dispatch `uncertain` on the desk
   and never sends it again, as the outbox does for a typed prompt (R5.4).
2. **The prompt.** It holds the task's request, the step's prompt, `instructions.md`, the writing
   guide, and three rules: open one pull request against the default branch, put the line
   `Priory-Task: <token>` in its body, and write any open question under `## Questions` in the
   body instead of waiting for an answer. The token is random and belongs to this run.
3. **Sleep.** The task is `asleep`, with waits the daemon registers: a pull request with the
   token, or the deadline. `asleep` keeps its meaning for the runner: no process there. A remote
   session may be working, and `priory tasks` shows `asleep (cloud <id>)` so a person can tell.
4. **The claim.** The intake's `github.pull_request.opened` message carries no body
   ([events.md](../reference/events.md)). So for each pull request opened in the repository of a
   task that waits on a token, the daemon fetches the body with `gh pr view`, as a stored effect
   that is retried. A body with the token makes the task own the pull request and its branch. The
   first one wins. A second pull request with the same token is recorded and left alone. The body
   is untrusted text: the daemon reads the token and nothing else from it.
5. **The result.** The daemon stores the run's result itself: outcome `opened`, the pull request's
   title as the summary, its head as the commit. The task moves on, usually to the human step
   that reads it.
6. **After that** the task is an ordinary task with a pull request: its checks gate
   ([waits.md](../daemon/waits.md#done-and-checks)), its review feedback and its merge step.

### When Priory stops listening

Priory cannot stop a remote session. It can stop listening to one. A run's token is live from its
dispatch until one of these retires it:

- the claim, once the task has left its cloud step and no feedback wait is open;
- a `failed` dispatch, at once;
- the `silent` outcome, when `next.silent` moves the task to another step;
- a cancel, a revive or a drop of the task.

A task that blocks on a silent session keeps its token live, and its place under `[cloud] max`,
so a person's resume can still end in a claim. An `uncertain` dispatch keeps it too, since the
prompt may have been sent: the token retires when the person cancels the desk item, or retries,
which dispatches with a new token.

A pull request that arrives with a retired token is never claimed. It gets a desk item, `late
pull request #N from cloud session <id>, after task 12 moved on`, for a person to close or to hand
to a new task. So a session that wakes up after a local fallback did the work cannot give one
task two pull requests.

### Feedback to the session

Feedback routes to the task because the task owns the pull request. What differs is the delivery.
When a wait fires for a cloud task, the daemon sends the same line a local agent would read, then
the event's body, with `claude -p MSG --cloud ID`. A red check goes the same way.

The message goes through the outbox's states: stored, attempted, then confirmed when the command
exits 0. No hook says the session is idle, so the daemon sends without waiting. After a message,
the task waits for a new head commit on the pull request, or a deadline.

Answers to a person's questions cannot come back the other way. A session that needs a decision
writes it under `## Questions`. The human step that reads the pull request sees it, and the
person's reply is feedback like any other.

### A silent session

A session that does nothing looks like a session that is still working. Only a deadline tells
them apart.

- No pull request with the token after the step's `timeout`, 2 hours when unset: the daemon sends
  one message, `Open the pull request now, as a draft that says what blocks you if it is not
  ready`, and waits 30 more
  minutes.
- Still none: the step ends `silent`. `next.silent` can lead to a local step that does the work
  with another agent. Without it, the task blocks with `cloud session <id> opened no pull request
  in 2h30`, and the desk offers resume, which sends a message, and cancel.
- After feedback, no new commit and no reply on the pull request within the same deadline: the
  same nudge, then a blocked task.

A branch with no pull request counts as silent. Priory cannot match a branch to a task without the
token, which lives in the pull request body.

### Drift the coordinator saw

Cloud sessions start from the default branch at dispatch and do not see each other. Two kinds of
drift showed up in this repository.

**Numbered files.** Two sessions each added the next migration number. The same happens to ADR
numbers. Local tasks are protected by the hold on overlapping files
([runs.md](../daemon/runs.md#overlapping-files)), which reads the files a branch changed at the end
of each run. A cloud task's own branch stays at its base commit, and the session's branch is
unknown until the claim. So:

- At the claim, the daemon records the pull request's changed files, and the overlap hold then
  applies to the tasks queued after it.
- Before the human step, the daemon checks that the pull request merges cleanly into the default
  branch. If not, it sends the session `the default branch moved: merge it and fix the conflicts`
  and waits for a new commit.
- A conflict the files do not show, such as two migrations with the same number in different
  places, is the repository's to catch: a `run` code step after the cloud step runs the factory's
  own check and sends its output back the same way.

**Footers and shape.** A session adds its own closing line to pull request bodies and commits,
and orders the body its own way, because the factory's writing guide reaches it as prompt text and
not as a system prompt. The daemon lints the body at the claim against the factory's patterns:

```toml
[cloud]
forbid = ["Generated by \\[Claude Code\\]", "Co-Authored-By: Claude"]
```

A match is sent back as feedback once. If the next commit's body still matches, the human step's
ask says so. The daemon never rewrites the body: a person should see what the session wrote.

### Cost

A cloud run's tokens are unknown to Priory, since the transcript stays in the cloud. Its
`factory.step.ended` record carries `harness: claude-cloud` and no `tokens`. `priory costs`
already keeps such records apart as `tokens unknown for N records` and never prices them at `$0`
([trace.md](../daemon/trace.md#costs)). The report gains one line: the count of cloud runs, their
total time from dispatch to claim, and the messages sent.

The spend is real and lands on the person's Claude plan or usage. Since room does not limit cloud
runs, a cap does: `[cloud] max = 3` bounds the live tokens, and a task past it waits in the queue
with that reason. The cap counts the sessions Priory listens to. A session whose token was
retired may still be spending, and Priory cannot see or stop it. The how-to guide says to close
it by hand from the desk item's link.

### The laptop

A local run of the PRD's example implementer reserves 6 GB of memory and 20 GB of disk, and its
builds and tests take the CPU. A cloud run takes none of them: no process, no worktree, no build.
The room check admits it at once, and the agents slice is untouched.

The daemon does not need to stay awake either. A laptop can dispatch three tasks and close.
Offline is normal (Principle 5): when it comes back, the intake's next poll finds the pull
requests, and the claims happen then. The deadline counts from the dispatch, so a session that
finished while the laptop slept is not silent.

### What a factory gives up

- The tool guard and every denial record. Nothing in Priory limits what the session runs.
- `ask`, so no question reaches the desk mid-work, and Principle 7 holds only at the pull request.
- Proofs and `priory gate`. The pull request's checks are the only proof.
- `remember`, `finding`, `progress`, `search` and the factory's MCP servers.
- Per-agent credentials ([agent-credentials.md](agent-credentials.md)): the session's GitHub
  access is the cloud environment's.
- Token counts and the harness's telemetry.

So a cloud step fits work that a pull request can fully judge, and no other.

## The first slice: dispatch, claim and the deadline

1. `harness = "claude-cloud"` in the schema, and the check rules above.
2. The branch rule check before a dispatch, and the `priory/gate` status the daemon sets when a
   merge step is approved.
3. The dispatch, with its recorded attempt and the stored session id, and `[cloud] max`.
4. The token, the body fetch and the claim after a `pull_request.opened` event, the result the
   daemon stores, and the retired token's desk item.
5. The deadline, the one nudge, the `silent` outcome and the blocked task.
6. A cloud runs line in `priory costs`, and `priory runs` showing the cloud session's id.
7. A page `docs/daemon/cloud.md` with the duty table, its link in the daemon's README, the keys in
   [agents.md](../reference/agents.md) and [factory.md](../reference/factory.md), and a how-to
   guide with the branch rule.

Tests, through the CLI with a fake `claude` and a fake `gh` on `PATH` that record their
arguments, as the tests already stand in for the harness and for GitHub:

- With a default branch that does not require `priory/gate`, or exempts administrators, no
  `claude --cloud` runs and the task blocks with the message above. The same when the rules
  cannot be read.
- An approved merge step sets `priory/gate` on the approved commit and on no other. After a new
  head, the approval is asked again and the new commit has no status.

- A task at a cloud step runs `claude --cloud` once, with a prompt that holds the request, the
  step's prompt and a `Priory-Task:` line, stores the printed id, and is `asleep` with no tmux
  session and no worktree.
- With a runner that has no free memory, the cloud task still starts, and a local task waits.
- With `[cloud] max = 1`, a second cloud task stays queued with the cap as its reason.
- A `github.pull_request.opened` message as the intake publishes it, with no body, makes the
  daemon fetch the body. With the token in it, the task owns the pull request, stores a result
  `opened` with the head as commit, and moves to its human step.
- A body fetch that fails is retried, and the task stays asleep meanwhile.
- A pull request with another token, with none, or in another repository changes nothing. A
  second pull request with the same token is recorded and not owned.
- A daemon stopped between the recorded attempt and the stored id marks the dispatch `uncertain`
  and runs no second `claude --cloud`.
- With the clock past the deadline, the fake `claude` gets one `-p ... --cloud ID` message. Past
  the second deadline, the step ends `silent`, and the task follows `next.silent` or blocks.
- A pull request claimed after a restart, with the dispatch older than the deadline, is claimed
  and not `silent`.
- A blocked silent task that a person resumes claims a pull request that arrives afterwards. An
  `uncertain` dispatch that a person retries gets a new token, and a pull request with the old
  one is not claimed.
- A revive at the approved commit sets `priory/gate` to `failure` on it. A status changed by
  hand is corrected at the next event and at the daemon's start.
- After `silent` led to a local step, a pull request with the retired token is not claimed, adds
  the desk item, and leaves the task's own pull request alone. The same after a cancel.
- A retired token frees its `[cloud] max` slot, and a live one holds it across a restart.
- `claude --cloud` exiting 1, or printing no id, ends the step `failed` with its stderr.
- Each check rule fails with its line: a reversible cloud step, a cloud step with a `proof`, a
  cloud agent with `mcpServers`, a cloud step no human step approves and with no `autonomous`,
  and a path to `done` with no human step.
- `priory costs` prints the cloud line and `tokens unknown for 1 records`, and no `$0`.
- A `proptest` feeds the token reader random and mutated pull request bodies and asserts it
  returns or refuses without panicking.

## Later slices

1. Feedback: wait lines and red checks sent with `claude -p MSG --cloud ID` through the outbox,
   and the deadline after each message.
2. `priory check --repo` reads the branch rules ahead of time, so a factory learns of a missing
   rule before a task blocks.
3. Drift: the overlap hold from the claimed pull request's files, the clean-merge check before
   the human step, and the `[cloud] forbid` lint.
4. Questions: the daemon turns the `## Questions` section of a claimed pull request into the text
   of the human step's ask.
5. `next.silent` to a local agent with the same prompt, as a starter workflow.
6. Usage, when the CLI or an API reports a session's tokens.

## Open questions

1. **Is a cloud step reversible?** The brief for this note says only reversible steps whose
   result is a pull request may run there. The work is reversible. The report is a pull request
   that nobody approved opening, the starters mark `open-pr` irreversible, and `priory check`
   refuses an `approves` that names a reversible step. Recommendation: declare the step
   `irreversible`, as written above, and keep "reversible" as a rule about the work. A factory
   that already runs `open-pr` as `autonomous` writes the same reason here and loses nothing.
2. **Can the session set the gate's status, and who authors its pull request?** Unknown, and the
   merge gate depends on it. Recommendation: before the first slice, run one cloud session by
   hand against a scratch repository and try both: set a commit status, and merge with the rule
   on. Write the answers in this note. If the session can set the status, pin the rule to
   Priory's own GitHub App, and do not build the slice until that works.
3. **How does Priory find the pull request?** By branch name, by author or by a token. A session
   picks its own branch name, and the author is the same for every session. Recommendation: the
   token in the body. Check on the first real run that sessions keep the line, and fall back to
   asking for it in the nudge.
4. **Should the daemon strip a footer itself?** Code could remove a known line with no model.
   Recommendation: no. Lint and send it back once, so the body a person reads is the session's.
   Revisit if the same line returns on most pull requests.
5. **What happens to a message sent while the session works?** Unknown. Recommendation: test it
   by hand before later slice 1, and write the answer in `docs/daemon/cloud.md`. If a message
   interrupts the session, hold feedback until the pull request's head stops moving for a few
   minutes.
6. **Does a cloud session need a runner?** The task is still owned by one runner, which
   dispatches and claims. Recommendation: yes, unchanged. Ownership decides who acts on the
   events, and that is as true for a claim as for a wake.
7. **Is this a second adapter of the runtime boundary?** The trait in `runtime.rs` is shaped for a
   program in tmux. Recommendation: do not stretch it. A cloud run is a branch in the daemon's
   start and wake paths, with its own module, and the trait stays for harnesses that run in tmux.
